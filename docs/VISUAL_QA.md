# Visual QA

Visual QA는 화면을 눈대중으로만 확인하지 않고, Playwright로 라우팅 가능한 전체 사용자 화면과 주요 상호작용 상태를 반응형 경계 폭에서 스캔해 레이아웃 이상 후보를 구조화된 리포트로 남깁니다.

## 100% 커버리지 계약

전수 검사의 규범적 범위는 `contracts/visual-qa-coverage-v1.json`에 기계 판독 가능한 계약으로 고정합니다. 여기서 100%는 임의 길이 입력처럼 무한한 경우를 뜻하지 않고, 다음 유한 계약을 빠짐없이 실행한다는 뜻입니다.

- `src/components`와 `src/pages`의 모든 React 컴포넌트 심볼을 분류합니다. 파일 단위가 아니라 한 파일 안의 내부 컴포넌트까지 심볼 단위로 셉니다.
- 각 컴포넌트에 적용되는 데이터·권한·상호작용·시스템 상태를 선언하고, 불가능하다고 증명된 조합을 제외한 전체 곱을 실행합니다.
- Chromium과 WebKit, 계약에 등록된 세로·가로 viewport, 100%·200% 텍스트/줌, 색상·모션·safe-area·입력 환경 중 해당 컴포넌트에 적용되는 전체 조합을 실행합니다.
- 미분류 심볼, 등록되지 않은 상태, 실행 오류, 만료되거나 담당자가 없는 제외 항목은 모두 실패로 처리합니다.

계약 자체는 다음 명령으로 검증합니다.

```bash
npm run visual-qa:contract:test
npm run visual-qa:contract:check
```

현재 완료된 것은 1단계 **범위 계약**, 2단계 **AST exact-match 인벤토리**, 3단계 **근거 기반 분류 레지스트리**, 4단계 **컴포넌트 독립 렌더 하네스·시각 기준선 기반**입니다. 5단계 **컴포넌트 상태 매니페스트**를 진행 중입니다. 아래의 기존 513개 경로·상태 스캔과 모듈 export 하네스는 계속 유효하지만, hosted 컴포넌트와 전체 상태·환경 조합이 아직 연결되지 않았으므로 전체 100% 보장이 활성화된 상태는 아닙니다. 이 사실은 계약의 `implementation.fullGuaranteeActive`가 `false`인 것으로도 명시합니다. 이후 단계가 완료될 때마다 `pendingStages`를 제거하며, 모든 출시 게이트에 실제 실행 증거가 연결된 뒤에만 이 값을 `true`로 바꿉니다.

조합 제외는 단순한 시나리오 수 제한으로 허용하지 않습니다. 각 제약에는 사유, 담당자, 해당 불가능성을 검증하는 테스트 증거가 필요합니다. 컴포넌트 자체를 제외할 때도 사유, 담당자, 만료일, 추적 이슈가 모두 필요합니다.

### 컴포넌트 심볼 인벤토리

2단계 인벤토리는 TypeScript AST를 사용하므로 파일 하나를 컴포넌트 하나로 간주하지 않습니다. 함수 선언, 화살표 함수, `memo`, `forwardRef`, `lazy`, 클래스 컴포넌트, 익명 기본 export와 파일 내부의 비공개 PascalCase 컴포넌트를 각각 별도 심볼로 기록합니다.

```bash
npm run visual-qa:inventory:test
npm run visual-qa:inventory
npm run visual-qa:inventory:reviewed-check
```

결과는 `reports/visual-qa-component-inventory.json`에 생성됩니다. 분류 매니페스트가 완성된 후 사용하는 `npm run visual-qa:inventory:check`는 다음 중 하나라도 있으면 실패합니다.

- 매니페스트에 없는 신규 또는 기존 컴포넌트 심볼
- 이미 소스에서 삭제됐지만 매니페스트에 남은 심볼
- 계약에 없는 분류 값을 사용한 항목

인벤토리를 생성하는 명령 자체는 분류 전 현황을 조사할 수 있도록 성공합니다. `:check`는 소스와 매니페스트의 exact-match를 검증하고, `:reviewed-check`는 여기에 더해 `conservative-visual-default`가 하나도 남지 않았는지 확인합니다. 의미 검토가 끝나기 전에는 엄격 게이트가 의도적으로 실패합니다.

현재 `contracts/visual-qa-component-classifications-v1.json`에는 508개 파일의 후보 심볼 2,081개가 명시적으로 등록되어 있습니다. 이 중 JSX·React wrapper·class 근거가 있는 `visual` 1,002개, `grouped-gallery` 725개, DOM을 만들지 않는 `behavior-only` 9개, 정적 분석으로 React 컴포넌트가 아님을 확인한 `nonvisual` 345개입니다. `behavior-only`와 `nonvisual`은 사유·담당자·테스트 증거가 모두 있어야 하며, 근거 없이 자동으로 검사 범위에서 빠지는 심볼은 없습니다. 모듈 export로 직접 접근 가능한 시각 컴포넌트는 513개이고, 부모 안에만 존재하는 hosted 시각 컴포넌트는 489개입니다. 보수적 기본 분류는 0개이며 `visual-qa:inventory:reviewed-check`가 통과합니다.

### 테스트 전용 컴포넌트 하네스

`visual-qa-harness.html`은 운영 `AppRoutes`에 연결되지 않은 테스트 전용 진입점입니다. 하네스는 분류 매니페스트에서 모듈 export로 직접 접근 가능한 아이콘과 일반 시각 컴포넌트 발견 시나리오를 자동 생성합니다. `src/components`와 `src/pages`를 모두 동적 import 대상으로 포함합니다.

```bash
npm run visual-qa:harness:test
npm run visual-qa:harness:dev
```

개발 서버에서 `/visual-qa-harness.html?component=<component-id>`를 열면 선택한 export를 격리된 표면에 렌더링합니다. 준비·실패 상태는 `window.__BEGA_VISUAL_QA_HARNESS__`와 `html[data-vqa-harness-state]`에 함께 기록되어 Playwright가 빈 화면을 성공으로 오인하지 않도록 합니다. 파일 내부 심볼처럼 `renderAccess: hosted`인 항목은 부모 시나리오와 실행 계측이 추가되기 전까지 직접 렌더 완료로 계산하지 않습니다.

전체 자동 아이콘 스모크는 다음 명령으로 테스트 서버 시작부터 Chromium 검사, 서버 종료까지 수행합니다.

```bash
npm run visual-qa:harness
```

현재 모듈 export로 접근 가능한 아이콘 667개가 이 스모크에 등록되어 있으며, 상태의 component ID와 실제 격리 surface의 component ID가 모두 일치하고 렌더된 DOM 자식이 있어야 통과합니다. 최신 전수 검증은 667/667 통과했고 결과는 `reports/visual-qa-icons-harness-smoke.json`에 기록됩니다.

일반 시각 컴포넌트의 무인자 발견 프로브는 다음 명령으로 실행합니다.

```bash
npm run visual-qa:harness:component-probes
```

현재 소스의 모듈 export 513개 전부가 발견 시나리오에 등록되어 있습니다. 최신 안정 발견 프로브는 모듈 export가 518개이던 시점의 296개 자동 렌더·PNG 생성 성공, 222개 상태/props 어댑터 필요 결과이며, 현재 인벤토리와 동일한 513개 기준 재실행은 아직 수행하지 않았습니다. 이 발견 프로브의 성공은 최종 상태 커버리지를 뜻하지 않으며 `finalCoverage: false`로 고정되어 있습니다. 실패는 `empty-render`, `missing-props`, `missing-provider`, `module-load`, `harness-timeout`, `screenshot-capture`, `render-error` 등으로 분류해 상태 매니페스트 작업의 입력으로 사용합니다. 같은 실행에서 아이콘은 667/667개의 고유 PNG 기준선을 생성했습니다.

브라우저 실행은 작업자별 context를 사용하고 각 컴포넌트를 새 page와 초기화된 local/session storage에서 렌더합니다. 기본 엔진은 시스템 Chrome이며 `VISUAL_QA_HARNESS_BROWSER=chromium`을 지정하면 설치된 Playwright 번들 Chromium만 사용합니다. 같은 모듈의 여러 export는 한 작업자에서 순차 처리해 Vite 동적 변환 경합을 막고, 서로 다른 모듈만 병렬화합니다. lazy chunk·CSS·이미지 같은 같은-origin 하네스 자산만 750ms 동안 조용해질 때까지 기다리고 `/api` 및 `/api/` 폴링은 안정화 판단에서 제외합니다. 따라서 Suspense fallback을 최종 성공으로 오인하지 않으면서 폴링 화면도 무한 대기하지 않습니다. 렌더 상태를 상호작용 selector보다 먼저 검증해 원래의 모듈·렌더 오류가 timeout으로 가려지지 않으며, 브라우저 인프라 유형의 실패만 새 page에서 1회 재시도하고 `attempts`, `retryHistory`, `recovered`로 사실을 보고합니다. 스크린샷은 viewport clip이 아닌 실제 surface element 전체를 캡처해 화면보다 긴 상태도 아래 내용까지 증거에 포함합니다. 외부 origin 요청은 차단하고 같은 origin의 `/api` 및 `/api/` 요청은 `VISUAL_QA_HARNESS_STUB` 503 응답으로 대체하므로 실제 백엔드나 외부 야구 데이터에 접근하지 않습니다. 프로덕션 빌드의 HTML·JavaScript·Vite manifest에 하네스 경로, `src/visual-qa/` 소스 경로, `__BEGA_VISUAL_QA_HARNESS__` 전역 센티널 중 하나라도 나타나면 `bundle-guard`가 `visual_qa_production_isolation` 실패로 빌드를 중단합니다.

특정 ID만 재검증하거나 성공 surface를 PNG 기준선 후보로 캡처할 수 있습니다. 상태 하네스에 컴포넌트 ID를 주면 해당 컴포넌트의 등록된 모든 상태 시나리오로 확장되고, 정확한 시나리오 ID를 주면 한 건만 실행합니다.

```bash
VISUAL_QA_HARNESS_COMPONENT_IDS='src/components/example/Example.tsx#Example' \
VISUAL_QA_HARNESS_SCREENSHOTS_DIR=reports/visual-qa-component-screenshots \
npm run visual-qa:harness:component-probes
```

스크린샷 파일명은 컴포넌트 ID의 읽을 수 있는 slug와 SHA-256 접미사로 만들어 충돌과 파일명 길이 초과를 방지합니다. 보고서가 현재 실행에서 생성한 이미지 경로만 참조하므로 디렉터리의 이전 파일을 전수 결과로 오인해서는 안 됩니다. 4단계는 이 격리 렌더·안정화·캡처 기반과 전 심볼 자동 시나리오 등록까지를 완료 조건으로 삼습니다. 모든 hosted 컴포넌트와 데이터·권한·상호작용 상태 조합의 기준선 등록은 5단계 이후의 완료 조건이며, 그 전에는 전체 100% 보장으로 계산하지 않습니다.

### 컴포넌트 상태 매니페스트

5단계의 규범적 입력은 `contracts/visual-qa-component-states-v1.json`입니다. 분류 매니페스트의 `visual` 심볼 1,002개가 정확히 한 번씩 존재해야 하며 신규·누락·삭제된 stale ID를 허용하지 않습니다. 매니페스트는 등록 완료 항목과 남은 `pending` 항목을 모두 드러내며, 다음 명령으로 소스 분류와 동기화합니다.

```bash
npm run visual-qa:states:refresh
npm run visual-qa:states:test
npm run visual-qa:states
```

공용 `Skeleton`은 임의의 대표 크기 하나로 축약하지 않습니다. `scripts/visual-qa-skeleton-usage.mjs`가 실제 import를 추적해 모든 정적 `<Skeleton className="…">` 사용처를 AST로 수집하고, `contracts/visual-qa-skeleton-usages-v1.json`의 안정적인 usage ID와 exact-match를 검사합니다. 신규·삭제·동적 className은 게이트를 실패시키며, 현재 104개 사용처의 고유 크기·폭·모서리·레이아웃 조합 79개가 상태 매니페스트에 그대로 연결되어 있습니다.

```bash
npm run visual-qa:skeleton:test
npm run visual-qa:skeleton:check
npm run visual-qa:skeleton:refresh
```

`registered` 항목은 다음을 모두 선언해야 합니다.

- 모듈 export는 실행 가능한 `adapterId`와 필요한 경우 프로덕션 `render.styles`, hosted 심볼은 하나 이상의 `hostScenarioIds`
- `data`, `permissions`, `interactions`, `system` 네 축마다 계약에 등록된 값 목록 또는 비적용 사유·담당자·테스트 증거
- 컴포넌트 고유 prop·표현 분기는 `variants.dimensions`의 이름과 전체 값 목록, 분기가 없으면 증거가 있는 `variants.notApplicable`
- `default`가 아닌 상호작용 값은 단일 `selector` 또는 여러 `targets[{id, selector}]`와 실행 action·사유·담당자·테스트 증거를 가진 `interactionPlans` 항목
- 불가능한 조합을 제외할 때 `excludeWhen`과 사유·담당자·테스트 증거

조합기는 공통 상태 축과 컴포넌트 고유 변형 차원의 전체 카테시안 곱을 만들고 증거 있는 `excludeWhen`만 제거합니다. 조합 수 상한이나 임의 샘플링은 허용하지 않으며, 제약이 모든 조합을 제거해도 실패합니다. 여러 상호작용 대상이 선언되면 대상 ID마다 별도 조합과 시나리오 ID를 생성합니다. 현재 상호작용 실행기는 hover, 키보드 `:focus-visible`, 캡처 시점까지 유지되는 `:active` pressed 상태를 실제 브라우저에서 만들고 CSS pseudo-state를 재검증합니다. 키보드 포커스가 성립한 직후에는 포인터를 화면 밖으로 이동해 긴 element screenshot 확장 중 다른 컨트롤의 hover가 섞이지 않게 합니다. 실행되지 않거나 효과가 확인되지 않은 상호작용은 실패로 기록됩니다. `npm run visual-qa:states`는 진행 중인 pending 수를 보고하기 위해 성공하지만, 출시용 완전성 게이트는 다음 명령이며 pending이 하나라도 있으면 실패합니다.


## 실행

```bash
npm run visual-qa
```

이 명령은 프로덕션 번들을 빌드하고 로컬 preview 서버를 띄운 뒤 스캔합니다. 결과는 다음 위치에 생성되며 Git에는 포함되지 않습니다.

- `visual-qa/report.html`: 사람이 검토하는 대시보드
- `visual-qa/report.json`: AI 리뷰 또는 후속 자동화가 소비할 구조화 데이터
- `visual-qa/screenshots/`: 문제가 탐지된 경로와 폭만 캡처한 이미지

스캔 중에는 같은 상위 경로의 임시 디렉터리에 결과를 만들고, 리포트와 스크린샷이 모두 완성된 뒤 세 관리 결과물만 롤백 가능한 단계로 교체합니다. 브라우저 시작이나 측정이 중단되면 직전의 완전한 리포트와 이미지가 그대로 유지되며, 출력 디렉터리의 다른 운영자 파일은 건드리지 않습니다.

같은 프로세스에서 같은 출력 경로로 들어온 publish는 순서대로 처리하고, 다른 프로세스와 겹치는 publish는 `.visual-qa.commit.lock`으로 거부합니다. Lock에는 owner PID, 생성 시각, 이전 artifact 목록과 staging/backup 경로를 기록합니다. Publish 중 프로세스가 강제 종료되면 다음 실행이 owner 종료를 확인한 뒤 backup에서 직전 완전한 세트를 자동 복원합니다. 세 결과물 교체가 끝나면 unlock 전에 완료 marker를 기록하므로, unlock만 실패한 경우에는 새 완전한 세트를 보존합니다. Lock metadata가 손상된 경우에는 자동 삭제하지 않고 명시적 오류를 내므로, lock만 지우지 말고 함께 남은 backup과 output 상태를 먼저 확인해야 합니다.

기본 스캔은 `AppRoutes.tsx`에서 감사 대상으로 분류된 33개 경로를 모두 사용합니다. 공개 홈·인증, 예측, 메이트 목록/생성/상세/신청/채팅/관리/체크인, 응원석 목록/북마크/상세/작성/수정, 구장, 순위, 스토브리그, 공지·약관, 마이페이지·메시지·공개 프로필, 관리자 화면이 포함됩니다. 폭은 320px부터 1440px까지 모바일·태블릿·데스크톱 경계와 내비게이션 전환 구간 14개를 사용합니다.

라우트 진입만으로 열리지 않는 다음 UI도 별도 상태 시나리오로 검사합니다.

- 공개·인증 모바일 메뉴
- 메이트 필터 바텀시트
- 마이페이지 티켓 등록 모달
- 인증 챗봇 패널

기본 조합은 경로 462개와 상태 51개, 총 513개 시나리오입니다. 챗봇은 모바일 전체 화면과 태블릿·데스크톱 고정 패널을 모두 엽니다. 파라미터 경로는 내부 정적 fixture로 메이트 상세·신청·채팅·관리·체크인, 응원글 상세·수정, 공개 프로필의 채워진 화면을 렌더링합니다. 따라서 성공 상태와 데이터가 긴 상태를 확인하면서도 실제 백엔드나 외부 데이터에는 접근하지 않습니다.

## 탐지 항목

- 페이지 가로 overflow
- `overflow: hidden/clip`에 의한 콘텐츠 잘림
- 독립된 조작 요소 간 겹침
- 모바일의 작은 터치 영역
- 서로 너무 붙은 조작 요소
- 모바일 뷰포트를 과도하게 가리는 fixed/sticky 요소

조작 요소 겹침과 간격 검사는 화면 안 요소의 사각형을 공간 버킷으로 묶어 가까운 후보끼리만 비교합니다. 따라서 실제 API 데이터로 DOM이 커져도 모든 요소 쌍을 무조건 비교하지 않습니다.

열린 모달은 `aria-modal="true"` 또는 `data-vqa-active-surface="true"`로 활성 표면을 식별해 배경 컨트롤을 검사 대상에서 제외합니다. 체크박스와 라디오는 연결된 `label`이 있으면 실제 레이블 클릭 영역을 터치 크기로 측정합니다.

리포트 issue는 `severity`, `type`, `viewport`, `selector`, `description`, `evidence`, `likelyCause`, `suggestedFix`, `confidence`를 포함합니다. 기본 모드는 후보를 사람에게 보여 주는 용도이므로 issue만으로 명령을 실패시키지는 않지만, 페이지 로드나 측정 실패는 항상 실패로 처리합니다.


경로와 폭을 좁히거나 CI용 실패 기준을 지정할 수 있습니다.

```bash
  --routes /home,/cheer \
  --widths 320,390,767,768,1024 \
```

## 의도된 예외 표시

수치 탐지기는 의도된 장식이나 겹침까지 제품 결함으로 단정하지 않습니다. 다음 속성으로 설계 의도를 명시할 수 있습니다.

```tsx
<div data-vqa-ignore>{/* 장식용 overflow */}</div>

<div data-vqa-overflow="allowed">{/* 의도적으로 잘리는 marquee track */}</div>

<div data-vqa-overlap="allowed">
  {/* 의도적으로 겹쳐 배치한 컨트롤 */}
</div>

<nav data-vqa-content-overlay="allowed">{/* 스크롤 여백이 확보된 고정 탭바 */}</nav>

<div data-vqa-touch-target="compact">{/* 24px 및 4px 간격을 지킨 고밀도 달력 */}</div>
```

`data-vqa-ignore`는 해당 하위 트리를 모든 detector에서 제외합니다. `data-vqa-overflow="allowed"`는 의도된 overflow/clipping 검사만, `data-vqa-overlap="allowed"`는 overlap 및 조작 요소 간격 검사만 제외합니다. `data-vqa-content-overlay="allowed"`는 스크롤 콘텐츠와 고정 탭바의 겹침만 허용해 다른 fixed 요소와의 충돌은 계속 검사합니다. `data-vqa-touch-target="compact"`는 실제 크기 24px 및 4px 간격을 확보한 고밀도 조작 영역의 40px 편의 권고만 제외하며, 24px 미만 결함은 계속 탐지합니다. 실제 결함을 숨기는 용도로 사용하지 말고, 의도가 명확한 컴포넌트에만 좁게 적용합니다.

## 재현성과 데이터 안전

기본 실행은 기존 reflow audit의 내부 fixture와 API stub을 재사용하므로 실제 백엔드, 운영 계정, 외부 야구 데이터에 접속하지 않습니다. 의도적으로 신뢰된 내부 백엔드를 확인할 때만 `VISUAL_QA_ALLOW_API=1`을 설정합니다. 보호 경로까지 실 API로 확인할 때는 운영자가 직접 만든 Playwright 인증 상태 파일을 `VISUAL_QA_STORAGE_STATE=path/to/storage-state.json`으로 함께 지정해야 하며, 이 파일은 저장소에 커밋하지 않습니다.

현재 경로 스캐너가 보장하는 범위는 라우팅 가능한 33개 화면, 위의 주요 오버레이 상태, 내부 fixture로 정의한 대표 성공/콘텐츠 상태입니다. 새 라우트는 기본 경로와 상태 시나리오에 등록해야 하며 라우트 누락은 테스트에서 실패합니다. 전수 계약의 최종 보장은 이 경로 검사에 컴포넌트 심볼·상태·환경 실행 증거가 모두 합쳐졌을 때만 성립합니다.

외부 AI 리뷰는 1차 리포트의 오탐 기준이 안정된 뒤 `report.json`과 문제 스크린샷만 전달하는 별도 단계로 추가합니다. 모든 정상 화면을 외부 모델로 보내거나 자동으로 코드를 수정하지 않습니다.
